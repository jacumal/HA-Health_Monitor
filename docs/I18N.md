# Internationalization and localization (i18n)

## Product requirement
HA Health Monitor is intended for an international audience. Multilingual support is part of the product foundation and must be implemented alongside the first functional features, not postponed until after the UI is complete.

## Initial language scope
- English (`en`) is the canonical source language and fallback.
- Spanish (`es`) is included in the initial release.
- The translation architecture must support adding further languages by adding catalogs, without modifying application logic.

## Coverage
Translate all user-facing content:
- Integration setup/config flow and options flow.
- Entity display names, descriptions and service descriptions where supported by Home Assistant.
- Lovelace card titles, editor controls, tooltips, helper text and validation messages.
- Statuses, severity labels, issue summaries and diagnostic explanations.
- Troubleshooting recommendations, verification steps and notifications.
- Empty, loading, error, unsupported, partial coverage and setup-required states.
- Accessibility labels and announcements.

Internal identifiers must remain stable and language-neutral: entity IDs, service IDs, config keys, enum values, rule IDs and incident IDs are not translated. User-provided entity/device names remain as supplied.

## Locale behavior and formatting
- Follow the Home Assistant user's language/locale where the platform exposes it.
- Use locale-aware formatting for dates, times, durations, numbers, decimal separators and percentages.
- Respect Home Assistant unit preferences for measurements where possible.
- Do not manually append translated unit abbreviations if HA formatting utilities can provide correct localized output.
- Use complete translatable messages with named placeholders and pluralization; avoid sentence-fragment concatenation.

## Fallback and translation quality
- English is the fallback for missing keys.
- Never show raw translation keys or blank UI labels.
- Preserve original technical error text when needed for troubleshooting, with a localized explanation alongside it.
- Translation catalogs must be reviewed for meaning and terminology consistency; machine translation alone is not a release-quality review.

## Implementation shape
- Backend uses Home Assistant's supported translation mechanisms and locale files (initially `translations/en.json` and `translations/es.json`, plus any platform-required string catalogs).
- Frontend maintains its own locale catalogs because it is independently distributed. Keep keys consistent and documented; use a small locale resolver/formatter rather than embedding translations in components.
- Avoid external translation services or network calls at runtime.
- Include catalog validation in CI: missing keys, unused/obsolete keys, placeholder parity and valid plural forms.
- Test English fallback, Spanish rendering, plural forms and locale-specific date/number formatting.

## Contribution workflow
1. Add the new locale catalog based on the English source.
2. Preserve all translation keys and named placeholders.
3. Run catalog and UI tests.
4. Review terminology and screenshots in the target locale.
5. Document the new language in the supported-language list.
